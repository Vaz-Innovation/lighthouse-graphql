# Performance at scale

A Rails process is long-lived: it builds the schema once at boot (before forking,
with Puma's `preload_app!`) and reuses it for every request. So PHP Lighthouse's
per-request schema and query caches mostly solve a problem Rails does not have.
Large schemas and high traffic still benefit from three options. **All are off
by default**; enable the ones your app needs.

| Option | What it does | Turn it on when |
| --- | --- | --- |
| [`schema_cache`](#schema-cache) | Caches the built schema document in `tmp/cache` | The schema is large and boot time matters (autoscaling, serverless, CI) |
| [`watch_sdl`](#reloading-the-sdl-in-development) | Reloads the app when a `.graphql` file changes | Developing; typically `Rails.env.development?` |
| [`persisted_queries`](#persisted-queries) | Apollo's Automatic Persisted Queries, optionally an allowlist | Large queries, CDN caching of `GET`s, locking the API down to known operations |

[`@defer`](#deferring-fields-experimental) (experimental) is a fourth, a plugin of the schema.

## Schema cache

```ruby
Lighthouse.configure { |config| config.schema_cache = Rails.env.production? }
```

Building a schema parses the SDL, injects directive definitions, runs the
manipulators (pagination types, `whereConditions` inputs, …), parses the result
and builds the executable schema. The cache stores the parsed, manipulated
document, so a boot skips everything up to that last step.

Measured on synthetic schemas (one machine; orders of magnitude, not promises):

| Schema | Without cache | Cached boot |
| --- | --- | --- |
| 150 models (≈1,000 types) | 260 ms | 145 ms |
| 600 models (≈4,300 types) | 1,060 ms | 560 ms |

It works the way Bootsnap does: a content-addressed file in
`tmp/cache/lighthouse` (`config.schema_cache_path` to move it).

- **The key.** It covers the SDL, the Lighthouse, graphql-ruby and Ruby versions,
  the registered directive and type definitions, the manipulators' source and the
  configuration they read. Change any of them and the next boot rebuilds, so a
  stale schema cannot be served and there is nothing to clear by hand.
- **Writes.** They are atomic, so concurrent boots never read half a file. Only
  the current entry is kept.
- **Errors.** An unreadable file is a cache miss, never an error.

To ship a warm cache, build it where the release is built (e.g. a Docker image
layer):

```shell
bin/rails lighthouse:cache        # writes tmp/cache/lighthouse/schema-<key>.bin
bin/rails lighthouse:clear_cache  # deletes it (never required: keys change on their own)
```

Unlike PHP Lighthouse's `lighthouse:cache`, forgetting to run it is harmless:
the first boot writes the cache.

## Reloading the SDL in development

```ruby
Lighthouse.configure { |config| config.watch_sdl = Rails.env.development? }
```

Rails' reloader watches Ruby files, not `.graphql` ones, so without this an SDL
edit only shows up after restarting the server. With it, the folder of
`config.schema_path` joins `config.watchable_dirs`, and an edit to any `.graphql`
file below it reloads the app, and with it the schema, on the next request, like
a Ruby change. The reload also rewrites the IDE helper files (`config.ide_helper`). This relies on the schema class living
in an autoloaded file, as `app/graphql/app_schema.rb` does.

## Persisted queries

```ruby
Lighthouse.configure do |config|
  config.persisted_queries = true
  config.persisted_queries_ttl = 1.week.to_i   # optional; default: until the store evicts
end
```

This is the [Automatic Persisted Queries](https://www.apollographql.com/docs/apollo-server/performance/apq/)
protocol, as Apollo Client (`createPersistedQueryLink`), urql and PHP
Lighthouse speak it:

1. The client sends `extensions: { persistedQuery: { version: 1, sha256Hash } }`
   without the query.
2. A known hash runs. An unknown one answers `PersistedQueryNotFound`, and the
   client retries with the query, which is checked against the hash and stored
   in `config.persisted_queries_store` (default: `Rails.cache`).
3. With the feature off, clients get `PersistedQueryNotSupported` and simply
   keep sending queries.

The generated controller runs requests through
`Lighthouse::GraphQL::PersistedQueries.execute`. A hash fits in a URL, so add a
`GET` route and CDNs can cache responses under the `Cache-Control` header that
[`@cacheControl`](caching.md#cachecontrol) computes. Rack's ETag middleware adds
an `ETag` too:

```ruby
# config/routes.rb
post "/graphql", to: "graphql#execute"
get  "/graphql", to: "graphql#execute"
```

Parsing and validating a query costs well under a millisecond, so this is about
bandwidth, CDN caching and control, not CPU.

### Trusted documents: a manifest and an allowlist

Large APIs often accept only the operations their own clients ship. Point
Lighthouse at a manifest generated by the client build, either Apollo's
persisted query manifest
(`{ "operations": [{ "id": "<sha256>", "body": "query …" }] }`) or a plain
`{ "<sha256>": "query …" }` object:

```ruby
config.persisted_queries_manifest = Rails.root.join('persisted-queries.json')
config.persisted_queries_only = Rails.env.production?
```

- The manifest's operations are served from memory, so a cache eviction can
  never drop them. The file is reloaded when it changes, and an id that is not
  the SHA-256 of its body is rejected.
- The manifest can also be a Hash of operations, or a callable answering a Hash
  or a path, called for every persisted query: to read what a frontend build
  (Vite, graphql-codegen's persisted documents) writes somewhere of its own. A Hash
  is checked once, until its content changes; keep the callable cheap (memoize the
  parsed file), as it runs per request.

```ruby
config.persisted_queries_manifest = -> { ViteManifest.persisted_documents } # a Hash, memoized
```
- With `persisted_queries_only`, nothing else runs, and arbitrary queries get
  `Only persisted queries are allowed.` (`PERSISTED_QUERY_NOT_IN_LIST`).

Check in CI that a schema change does not break an operation already shipped to
clients:

```shell
bin/rails lighthouse:persisted_queries:verify SCHEMA=AppSchema
```

## Deferring fields (experimental)

**Experimental: not enabled by default, not guaranteed to be stable.**

Deferring fields lets a client get the data it needs to render the most important content
as fast as possible, and the rest in the background, in later parts of the same response.
Lighthouse supports `@defer` (and `@stream`) through a plugin of the schema, as PHP Lighthouse
does through an extension, but as the
[specification draft](https://github.com/graphql/graphql-spec/pull/1110) (RFC stage 2) has them:
`@defer` goes on a fragment, not on a field.

```graphql
query Feed {
  posts(first: 10) {
    data {
      title
      ... @defer(label: "details") { author { name } comments { data { body } } }
    }
  }
}
```

The draft can still change, and the plugin, the settings and the payloads may change with it
before it reaches stage 3. Clients that read the draft's format include Apollo Client
(`GraphQL17Alpha9Handler`), graphql-js 17 and Relay; those on the older
`Defer20220824Handler` format (Apollo Router's) are answered a whole response.

### Setup

Use the plugin in the schema class, and route the clients that prefer a streamed response to a
controller that streams:

```ruby
# app/graphql/app_schema.rb
class AppSchema < Lighthouse::GraphQL::RbLightHouse.get_schema(options: { ... })
  use GraphQL::Dataloader
  use Lighthouse::GraphQL::Defer          # adds @defer and @stream
end

# app/controllers/graphql_streaming_controller.rb
class GraphqlStreamingController < GraphqlController
  include ActionController::Live          # streams the response

  # One endpoint: rate_limit and @throttle count both controllers' requests together.
  def self.controller_path = superclass.controller_path
end

# config/routes.rb
post '/graphql', to: 'graphql_streaming#execute', constraints: Lighthouse::GraphQL::Defer::Streaming
post '/graphql', to: 'graphql#execute'
```

`GraphqlController` stays as `lighthouse:install` wrote it. `ActionController::Live` runs an action
in a thread of its own, with what that changes (the database connection the thread checks out,
thread-locals, errors once the response is on its way), so only the requests that stream should run
in it: `Lighthouse::GraphQL::Defer::Streaming` routes there the requests whose `Accept` header
prefers `multipart/mixed`, and every other request (JSON, batches, uploads) goes to the plain
controller, as before. A plain controller answers a client that prefers `multipart/mixed` with one
ordinary response, the deferred fields in it.

Without the plugin the schema has no `@defer`, as the specification asks of a server that does
not implement it.

### Configuration

Two settings keep a deferred response from running too long, PHP Lighthouse's
`defer.max_nested_fields` and `defer.max_execution_ms`, with their meaning. `0`, the default, is
no limit.

```ruby
Lighthouse.configure do |config|
  config.defer_max_nested_fields = 3       # rounds of nested deferred fragments
  config.defer_max_execution_ms = 2_000    # since the first pass started
end
```

A response goes in rounds: the first payload, then one payload for each round, which resolves
every fragment pending and announces the fragments those hold. Past `defer_max_nested_fields`
rounds, or once `defer_max_execution_ms` milliseconds have gone, the round that runs is the last:
it resolves the fragments it holds where they stand, without deferring them. See
[configuration.md](configuration.md#defer_max_nested_fields-and-defer_max_execution_ms).

### Writing @defer

`@defer` goes on an inline fragment or a fragment spread (`...Details @defer`), with `if` (defer
only when true; a variable is fine) and `label` (names the fragment in the response):

```graphql
directive @defer(if: Boolean! = true, label: String) on FRAGMENT_SPREAD | INLINE_FRAGMENT
```

To defer one field, as PHP Lighthouse's `field @defer { ... }` does, put it in a fragment of its
own: `... @defer { field { ... } }`. Fragments nest: one inside a deferred fragment arrives a round
after it.

The rules, from the draft and PHP Lighthouse. They hold for every query of the schema, streamed or
not (a graphql-ruby analyzer checks them before anything runs, and a query that breaks one is
answered the errors, without data):

- `@defer` is not allowed on a root mutation field, whose fields must run one after the other:
  "The @defer directive cannot be used on a root mutation field.", whether the fragment is inline or
  named. A fragment deeper in a mutation's response defers as in a query.
- In a subscription, `@defer` must be disabled: `if: false`, or a variable that is false for the
  request (one that is true is refused, as the draft forbids incremental delivery there).
- `label` is a string, not a variable, and no two `@defer` or `@stream` of the document share one
  (in any of its operations and fragments).
- `@skip` and `@include` on the fragment answer first: a fragment they leave out is neither
  deferred nor resolved.
- A fragment with `if` not false is always deferred, and completes. A field it selects that the
  rest of the query also asks for at the same path (itself, or through an inline or a named
  fragment) comes in the first payload as usual, resolved once, and is not sent again: in
  `{ ...UserWithParent ... @defer { parent { name } } }`, where `UserWithParent` also selects
  `parent { name }`, the fragment is pending, then completes with no data of its own. A fragment
  that adds selections to such a field (`... @defer { parent { email } }`) gets them, without
  `parent` resolving again, at the `subPath` of `parent`. Two fragments of a round that select
  one field send it once.
- A fragment on a type the object does not have runs nowhere, and one on a union with no type
  condition runs where it stands, as the specification has it.

### What the client gets

The first part is the response without the deferred fragments, and a `pending` entry for each
one, with a string `id`, the `path` of the object it will run on and its `label`. A fragment under
a list is pending once for each item. Then a part for each round: the `incremental` data of each
fragment, under its `id`, and the ids that are `completed`, with the `pending` entries of the
fragments that round found; the last part has `hasNext: false`.

```json
{ "data": { "posts": { "data": [{ "title": "Hello" }] } },
  "pending": [{ "id": "0", "path": ["posts", "data", 0], "label": "details" }], "hasNext": true }
{ "incremental": [{ "id": "0", "data": { "author": { "name": "Ana" }, "comments": { "data": [] } } }],
  "completed": [{ "id": "0" }], "hasNext": false }
```

An entry carries what was not sent yet: the fragments of a round at one path send one entry, under
the first one's `id`, and complete together; what a fragment adds to an object field already sent
comes in an entry of its own, at the field's `subPath` from the fragment's path:

```json
{ "data": { "user": { "parent": { "name": "Ana" } } },
  "pending": [{ "id": "0", "path": ["user"] }], "hasNext": true }
{ "incremental": [{ "id": "0", "data": { "name": "Bo" } },
                  { "id": "0", "subPath": ["parent"], "data": { "email": "ana@example.com" } }],
  "completed": [{ "id": "0" }], "hasNext": false }
```

The errors of a deferred field come with it, on its `incremental` entry, with the path the field
has in the response. A fragment's delivery is all or nothing: when a non-null field fails beyond
any part of it (its object, or an object it adds to at a `subPath`), it sends no data at all, and
its `id` is `completed` with the `errors`. The `extensions` that `BuildExtensionsResponse` and
`ManipulateResult` listeners add while a fragment runs are on its `incremental` entry too; an entry
that would carry nothing else (no data, no errors) is not sent, and its extensions go on the
part's own `extensions`, as those of a fragment that sends no data.

### Streaming lists (experimental)

`@stream` on a list field answers its first `initialCount` items (default 0) at once, and the
others in a later part. PHP Lighthouse has no `@stream`.

```graphql
directive @stream(if: Boolean! = true, label: String, initialCount: Int! = 0) on FIELD

query { posts(first: 50) { data @stream(initialCount: 5, label: "rest") { title } } }
```

```json
{ "data": { "posts": { "data": [ ... 5 items ... ] } },
  "pending": [{ "id": "0", "path": ["posts", "data"], "label": "rest" }], "hasNext": true }
{ "incremental": [{ "id": "0", "items": [ ... 45 items ... ] }], "completed": [{ "id": "0" }], "hasNext": false }
```

The field's resolver runs once and returns the whole list; `@stream` cuts it where `initialCount`
says, and the selections of the items that follow run in the next round, all together so the
Dataloader batches across them. A list of scalars streams too, and so does a paginated field's
`data`. A list that resolves to `null` is `null`. An item may carry `@defer`: its fragment is
announced with the items, at the index the item has in the list, and arrives after them. The rest
of a list is one batch: the specification allows a server to cut it as it pleases. The later items
run what every declaration of the field selects (`users @stream { id } ... on Query { users { name }
}`), and nothing of another field of the same name. Where that depends on more than the field's
object (a declaration under a type condition above it, or in another deferred fragment), the list
is answered whole.

`@stream` needs a list field (a validation error otherwise), follows the rules of `@defer` for
`label`, mutations ("The @stream directive cannot be used on a root mutation field.") and
subscriptions, and a negative `initialCount` is a field error: the field is `null`, with the error at
its path. The plugin adds a graphql-ruby trace module to the schema that uses it (and no other
schema built on the same types), which cuts the lists of every field of that schema, whenever the
field was defined, and changes no field; a field that is not streamed costs it a method call and a
fiber-local read.

### Transport

A controller streams the response, as `multipart/mixed` parts (graphql-over-http's incremental
delivery), when three things hold: the schema uses the plugin, the controller includes
`ActionController::Live`, and the request's `Accept` header prefers `multipart/mixed` (without the
older format's `deferSpec` parameter) to a JSON response: not at `q=0`, and ranked, by q and then by
order as Rails ranks types, before `application/json` and `application/graphql-response+json`
(`Lighthouse::GraphQL::Defer.stream_type`, which the route constraint and the controller share: the
header is read once). In every other case the whole response comes at once, the deferred fragments
in it, as the specification allows: a JSON client, `schema.execute`, a batch (a JSON array). A query
that defers nothing is answered as JSON, whatever the client accepts. A part's JSON is encoded as
`render json:` encodes any response.

Streaming needs a server that writes as the action goes (Puma; not a single-threaded buffering
one) and proxies that do not buffer: the response sends `X-Accel-Buffering: no` for nginx,
`Cache-Control: no-cache`, and a `Last-Modified` so `Rack::ETag` lets it through. Do not put
`Rack::Deflater` in front of it. Because `ActionController::Live` runs the action in its own
thread, keep thread-locals (`ActiveSupport::CurrentAttributes`) in mind in hooks of your own.
`@cacheControl` does not apply to a streamed response (`Cache-Control: no-cache`).

Once the first part is sent, the response can no longer be refused: a `@throttle` past its limit in
a later round is the field's error ("Rate limit for Query.x exceeded. Try again later."), and its
`with:` method is not called. A round that fails, or a part that cannot be written (a value of the
app's that does not encode), ends the stream all the same, with a last part that completes, with an
error, every id the client was sent and has not seen completed; the error goes to `Rails.error`.

### How it runs

- **The client's document, as it came.** It is never rewritten: validation, analysis, listeners
  (`StartExecution#query`), `query.query_string`, the operation's fingerprint and tracing see the
  document the client sent, streamed or not. graphql-ruby hands `@defer` its arguments, not its node;
  Lighthouse knows the node by the arguments graphql-ruby caches for it.
- **Every field resolves once.** The first pass leaves the deferred fragments out; each round
  then runs the pending fragments on the objects the passes before it loaded
  (`GraphQL::Query::Partial`), never by running their parents again, and leaves out what the
  response already holds. `@throttle`, `@guard`, `@cache`, events and the rest of a field's
  directives run in the pass that resolves the field; a mutation does not run twice. To reach an
  object field the response already holds, the plugin's trace module keeps, while a streamed
  response runs, the objects its fragments will need, in whatever trace mode the app picks. An app
  that gives a trace class of its own, leaving out the schema's trace modules, gets every response
  whole.
- **No N+1.** All the fragments of a round run in one multiplex, so the Dataloader batches across
  them: a deferred fragment under a list of 50 costs the queries it costs without `@defer`.
- **graphql-ruby's standard engine.** A streamed request runs as `schema.execute` runs one, with the
  schema's `query_class`, on graphql-ruby's standard execution engine, where the deferred rounds'
  `GraphQL::Query::Partial`s run, even when the schema opts into graphql-ruby 2.6's new engine
  (`default_execution_next`) for its other requests.
- **Validation and complexity cover the whole document**, before the first pass: the deferred
  fragments count for `max_complexity` and `max_depth`, as they would without `@defer`.
- **Events.** `StartExecution` and `EndExecution` fire for the first pass, and again for each unit a
  round runs (the fragments of one path on its object, or a stream's items), with the client's
  document; `EndRequest` after the last part.

### Differences from PHP Lighthouse

- **Fragments, not fields.** PHP Lighthouse's `@defer` goes on a field (`directive @defer(if:
  Boolean = true) on FIELD`); the draft's, and this one, on a fragment, with a `label`. A query
  written for PHP Lighthouse puts each deferred field in a fragment: `parent @defer { name }`
  becomes `... @defer { parent { name } }`.
- **The draft's format, not Apollo's 2018 one.** PHP Lighthouse answers `null` for a deferred field
  first, then chunks keyed by path (`{ "user.parent": { "data": ... } }`) and no `hasNext`. This
  leaves the field out of the first payload, and answers `pending`, `incremental`, `completed` and
  `hasNext`, which today's clients read.
- **One pass per round, not the query again.** PHP Lighthouse runs the whole operation again for
  each round, and answers what it already has from the previous result; this runs only the deferred
  fragments, on the objects already loaded. A field resolves once, and a mutation runs once.
- **`@stream` is added.** PHP Lighthouse has none.
- **A field asked for outside the fragment too is sent once, and the fragment still completes.**
  PHP Lighthouse (as Apollo) does not defer a field one of whose declarations is not deferred: the
  field, with everything any declaration selects of it, comes in the first payload. As the draft
  has it, the fragment here is deferred all the same: the field comes in the first payload with
  what the rest of the query selects of it, the fragment sends what it adds, and completes.
- **Non-null fields can be deferred.** PHP Lighthouse refuses `@defer` on a Non-Null field ("The
  @defer directive cannot be used on a Non-Nullable field.") because it answers `null` for it first;
  the draft's format leaves the field out instead, so nothing needs refusing.
- **The rules hold for every query.** PHP Lighthouse checks them as a deferred field resolves; here
  they are checked before anything runs, for every request, streamed or not.
- **The time limit counts milliseconds from the first pass.** `defer_max_execution_ms` starts when
  the first pass does; PHP Lighthouse's deadline is set when its `Defer` is built, as
  `microtime(true) + max_execution_ms * 1000`, a time in seconds plus the setting times a thousand
  (2000 reads as two million seconds).

## What is deliberately not cached

- **Query ASTs and validation results.** PHP Lighthouse caches them because PHP
  starts from scratch on every request. Here, parsing and validating a sizeable
  query takes about 0.2 ms and 0.6 ms. A shared store (Redis, Memcached) costs a
  network round trip, which is more than parsing, and validation can depend on
  the request's context, which a cache keyed by query text would skip.
- **Compiled Ruby.** Your app's code, and Lighthouse's, are already compiled
  and cached by Bootsnap (instruction sequences) and YJIT. The SDL is not Ruby,
  so there is nothing for them to compile.
